Part 2

Engineering audit

Gaps in the app itself, not the content. Nothing here requires touching the visual design. Build, typecheck, lint and all 15 tests pass; 504 pages prerender.

New · High

Chapter pages have no <h1> at all

Found in this pass. A chapter page's heading order is h2 Chapters → h2 Jump to a level → h2 Topics → h2 Your progress → h2 Tries. The sidebar's four headings come first, and the actual chapter title is an h2 buried behind them. There is no h1 on the page.

This mattered less when a topic was one page; now that every chapter is its own indexable route it is the strongest on-page signal Google looks for, and it is missing on all 504 of them. For screen-reader users navigating by heading, the document also reads as four navigation sections before any content.

components/reader/ChapterSheet.tsx — title renders as h2; Shell sidebar uses h2 for nav groups
New · Medium

No security headers

next.config.ts is empty and there is no middleware, so the app ships without CSP, X-Frame-Options, X-Content-Type-Options or Referrer-Policy. The reader injects chapter HTML with dangerouslySetInnerHTML — that content is authored by you, not user input, so this is hardening rather than an open hole, but a CSP is the thing that would contain a mistake in 30,000 lines of hand-written HTML.

next.config.ts — no headers() block, no middleware.ts
Not real

An unlabelled button on every page

Flagged by the automated accessibility sweep on all four page types.

✓ Not a real problem — it is the mobile drawer backdrop, which already carries aria-hidden="true" and tabindex="-1". Assistive tech never sees it. Recorded here so the next audit doesn't re-raise it.

Fixed

The site is invisible to search engines

No sitemap, robots, favicon, manifest, or Open Graph images — nothing indexable and every shared link a blank grey card.

app/ — sitemap.ts, robots.ts, manifest.ts, opengraph-image.tsx all absent

✓ Fixed — phase 1. All present, plus a generated favicon and apple-icon. Sitemap priority is weighted by how much of a topic is actually written.

No error boundaries at any level — one thrown error and the reader gets nothing.

✓ Fixed — phase 1. All three, in the notebook aesthetic; the 404 carries a rotated stamp like the rest of the site.

Sidebar progress always reported JavaScript, on every topic

setChapterDone was only called from /path, so in practice progress never got recorded and the whole system was decorative.

✓ Fixed — phase 1. A checkbox in the chapter footer, plus a subscription in progress so the sidebar meter updates live from anywhere it is ticked.

Fixed

Every chapter of every topic shipped to the browser at once

app/dsa/page.tsx was a client component importing all 504 KB of dsa-notes.ts — an 880 KB JavaScript chunk of pure prose to read one chapter.

app/dsa/page.tsx — "use client" + full content import

✓ Fixed — phase 2, the big one. Chapters are real routes rendered as server components. The 880 KB chunk is gone — verified no client chunk contains chapter prose. A reading page is 84 KB of HTML and 257 KB gzipped of framework JS, and every chapter is independently indexable.

Fixed

No tests and no CI

Zero test files, no runner, no GitHub Actions — every change verified by hand.

✓ Fixed — phase 2. Vitest with 15 content-integrity tests: ready-but-empty bodies, URL-safe chapter ids (they are route segments now), practice and syllabus wiring, aria-labels on every diagram. Proven to fail on a real break, not just pass. CI runs typecheck, lint, tests and build.

Fixed

The sidebar search box stole focus on every page load

Not in the original audit — it surfaced while testing phase 2. Radix's FocusScope pulls focus to its first tabbable child on mount, and the sidebar is always mounted, so the caret landed in the search input on every page. Keyboard shortcuts silently did nothing.

✓ Fixed — the focus trap mounts only while the mobile drawer is open.

Not real

A 3.4 MB editor chunk loads for readers who never open the editor

CodeMirror and the bundled TypeScript library dominate the build.

✓ Not a real problem — measured in phase 2 and the claim did not survive. The chunk is already lazy: it appears on no page's initial load, not even /practice. The first audit inferred this from total build size rather than from what a page actually requests.

Medium

Narration depends on an unofficial Microsoft endpoint

Known and accepted when it was chosen: msedge-tts reverse-engineers Edge's Read Aloud API. It can break without notice, needs --ignore-scripts on a fresh install, and has no fallback path.

app/api/tts/route.ts
Medium

No analytics, so content decisions are guesses

Nothing records which chapters get opened, where reading stops, or which searches return nothing. With 421 chapters left to write, that last signal in particular would tell you what to write next.

Medium

Search only covers the topic you're already in

The reader fetches one topic's index, so searching "caching" from DSA can't surface the System Design chapters that now cover it in depth — a real loss, because those two tracks genuinely overlap.

Medium

No offline support

The most valuable time to read interview notes is on a commute. A service worker caching visited chapters would cover it, and the content is static enough to make this low-risk.

Part 3

Can this content get you a $500K offer?

Short answer: not yet — and the reason has changed

It is no longer a coverage problem on the two hardest subjects. DSA and System Design are both written end to end at genuinely senior depth. The blocker now is that this is a library, not a gym. Sixty chapters of reading with zero problems trains recognition; an interview tests recall under time pressure with someone watching. Those are different skills, and only one of them is on the site.

$500K total compensation is senior-to-staff at a top payer: Google L6, Meta E6, Amazon L7, or senior at Netflix / OpenAI / Stripe. At that level the coding round is the entry ticket, not what decides the offer. Here is where the site stands against a real loop.

What a senior/staff loop weighs Share Content Can you practise it?
System design — the biggest lever at this level ~35% 24 / 24 written no prompts, no rubric
Coding / DSA — necessary, rarely the differentiator ~30% 34 / 34 written 0 problems
Behavioral & scope — influence, ambiguity, conflict, impact ~25% nothing on the site —
Domain / craft depth — language and runtime internals ~10% 2 of 24 JS, 0 of 41 Node 16 JS exercises exist

Share-of-loop figures are informed estimates, not published numbers; they move by company and by interviewer.

The uncomfortable one: behavioral is where the money actually moves

Candidates who can code get downlevelled from L6 to L5 — a six-figure difference — on the behavioral round, almost always for the same reason: they describe work they did instead of work they drove. Scope, influence without authority, decisions under ambiguity, disagreement handled well. The curriculum has no topic for this at all, and it is the cheapest gap on this page to close.

What would actually change the answer to "yes"

  • A problem bank for both finished tracks. ~150 DSA problems mapped to the 34 chapters, plus System Design prompts with a rubric. This is the single biggest gap between "I read it" and "I can do it".
  • A behavioral / staff-scope track. STAR structure, a story bank you fill in yourself, the L5-vs-L6 signal table, and how to talk about scope and influence.
  • A timed mock mode. Two chapters now teach a 45-minute framework — DSA A12 and the System Design walkthroughs. Nothing lets you rehearse either against a clock.
  • Language and runtime depth. JavaScript 2/24, Node 0/41. Senior loops probe the event loop, memory and concurrency directly, and this is also the part a JS-heavy résumé gets grilled on hardest.
  • Spaced repetition. 60 chapters is already more than you can hold. Without resurfacing, the early DSA chapters are gone by the time you interview.
  • Company-specific tracks. Meta's product-design bias, Google's algorithmic bar, Amazon's leadership principles — the same content, filtered per target.

An honest caveat about the site itself

No study site gets anyone an offer on its own. What this one can realistically do is make your preparation ordered, complete and free of blind spots — which is worth a lot, because most candidates prepare in a scattered way. The parts it cannot supply are reps against a real person, feedback on how you sound while thinking, and the actual project experience the behavioral round asks you to narrate.

Part 4

The plan

Reordered after this pass: making the finished tracks practisable now outranks writing more topics, because it is what converts reading into interview ability.

01

Fix what's broken

✓ shipped
  • SEO infrastructure: sitemap, robots, manifest, favicon, OG images
  • Error boundaries at every level
  • Topic-aware sidebar progress
  • "Mark as read" in the reader itself
02

Make it fast and keep it correct

✓ shipped 880 KB → 0 content JS

Done before writing more chapters, not after — the bundle problem compounds with every chapter added.

  • Content out of client components; chapters render on the server
  • Route per chapter, so one chapter loads one chapter
  • Vitest + 15 content-integrity tests, GitHub Actions CI
03

System Design — all 24 chapters

✓ shipped

Written to the same standard as the DSA advanced tier. The two end-to-end walkthroughs (URL shortener, news feed) carry the most weight — they are what the interview actually looks like.

04

Turn the finished tracks into a gym

next up ~3–4 sessions recall, not recognition

Promoted above the behavioral track after this pass: 58 chapters with zero problems is now the largest single weakness, and the runner to support it already exists.

  • ~150 DSA problems mapped across the 34 chapters, using the existing runner and test format
  • System Design prompts with a self-scoring rubric
  • A timed mock mode that runs the 45-minute framework under a real clock
  • Spaced repetition that resurfaces chapters you read weeks ago
05

The behavioral track

~1–2 sessions the downlevel guard

A new topic in the same shelf format: STAR structure, the L5-vs-L6 signal table, scope and influence framing, plus a story bank you fill in and reread before a loop. Small to build, disproportionate effect on offer level.

06

Fix what this pass found

~1 session
  • Give chapter pages a real h1, and demote the sidebar's nav headings so the document outline reads content-first
  • Add security headers (CSP, X-Frame-Options, Referrer-Policy) in next.config.ts
  • Cross-topic search, so DSA and System Design surface each other
07

Fill the remaining topics by interview relevance

ongoing

Not alphabetically, and not all of them. Suggested order: JavaScript (finish the 22) → Node → React → TypeScript → Databases → Security → Testing → the rest. Some topics may be worth cutting rather than writing — 22 HTML chapters will not move a staff-level loop.

08

Product polish

ongoing
  • Analytics on chapter reads, drop-off, and zero-result searches
  • Offline reading via a service worker
  • A narration fallback for when the unofficial TTS endpoint breaks
  • Full keyboard and screen-reader pass

If you only do one thing next

Build the DSA problem bank. Everything upstream of it is written, the runner and test format already exist, and it is the step that converts 58 chapters of reading into something an interview can actually measure. The behavioral track is the close second and the cheaper build — do it immediately after, or in parallel if you get bored.
