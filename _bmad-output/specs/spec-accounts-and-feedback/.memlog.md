- (direction) 2026-10-08 owner (Hinglish): in the future add user login so the owner can get user information and feedback from readers; also asked for a plan; the site is becoming a general developer platform, not JS-only.
- (note) Today: Next.js 16 on Vercel, no backend and no account; progress in localStorage (jsnotes:* and groundwork:* keys); privacy page states no account, no database; Vercel Web Analytics and Speed Insights, optional Sentry, a narrator route and a client-error route exist; script budget about 700 KB.
- (decision) Guest-first: the whole site keeps working with no account; login is optional and never gates reading, practice, checks or the mock; existing localStorage progress is never lost and is offered for import at first sign-in.
- (decision) Recommended auth: Supabase Auth (the owner already has a Supabase connector) with email magic link plus Google and GitHub; no passwords, so no password reset, breach or hashing surface.
- (capability) CAP-1 Feedback without an account: a reader can leave feedback with no login (per-chapter helpful or unclear vote with optional comment, report a wrong quiz or check answer, general feedback form, feature request).
- (capability) CAP-2 Optional sign-in: a reader can sign in with an email link, Google or GitHub, stay signed in across visits, sign out, and keep using the site as before if they never do.
- (capability) CAP-3 Minimal profile with consent: a signed-in reader can set display name, experience level, target roles, languages and topics they care about and optionally country, each field optional and consented separately, and edit or remove each.
- (capability) CAP-4 Progress sync: a signed-in reader's progress, streak, checks, placement and settings follow them across browsers and devices, merged from their local data at first sign-in without loss.
- (capability) CAP-5 Reader control of data: a signed-in reader can export all their data and delete their account and data, and the privacy page states exactly what is collected and why.
- (capability) CAP-6 Owner feedback inbox and insights: the owner can read, tag, mark answered and export feedback and see simple aggregates (signups, active readers, most-missed questions, chapters with most unclear votes) without any third-party tracker.
- (capability) CAP-7 Prompts at the right moment: a reader is asked for feedback only after real use (after N chapters, a pass or a fail), never twice for the same thing, always dismissible for good.
- (constraint) Privacy-first analytics: keep Vercel Analytics and Speed Insights; add no third-party trackers, ad tech, session replay or fingerprinting; no PII in logs, Sentry, analytics events or URLs.
- (constraint) Performance: keep static prerender of every content page and the home script budget; auth and feedback code load lazily and only on interaction or after idle; server routes only where a secret or a write needs them; auth state is client-side so no page becomes dynamic.
- (constraint) Security: Row Level Security on every table with owner-only reads for user data; feedback inserts rate-limited and spam-protected (honeypot plus per-IP limit, optional lightweight challenge); admin access by an explicit role, never by a client flag; secrets only on the server.
- (constraint) Legal: update the privacy page before any collection starts; explicit consent per profile field; data export and delete; India DPDP Act and GDPR basics; readers under 18 are not asked for profile data beyond what sign-in needs, and no marketing mail.
- (constraint) Sync is last-write-wins per key except progress marks and quiz records, which merge by union (a read mark never disappears because of a stale device); the server never trusts a client to set another reader's data.
- (decision) Rollout in phases, each shippable alone: phase 0 anonymous feedback (no login); phase 1 optional sign-in and profile; phase 2 progress sync; phase 3 owner dashboard and insights.
- (decision) Anonymous feedback uses a random per-browser id kept in localStorage only to dedupe votes; it is not linked to a person and is dropped when the reader signs in unless they choose to link it.
- (assumption) Data lives in a Supabase project in an Indian or Singapore region (closest to the readers); to confirm.
- (assumption) The owner is the only admin at first; moderation is manual.
- (assumption) Email links are sent by Supabase's built-in mail for development and a transactional provider on the owner's domain for production.
- (question) Which sign-in providers: email link plus Google and GitHub only, or also others?
- (question) Will login ever be required for any feature (for example cloud-saved boards, a leaderboard, certificates)? The spec assumes never.
- (question) Which region should the data live in, and is a data processing agreement with the host needed?
- (question) Who else may read feedback, and should any feedback be public (for example a roadmap voting board)?
- (question) How should spam and abuse be handled beyond rate limits (moderation queue, blocklist, captcha)?
- (question) Should an email address be required to leave feedback so the owner can answer, or stay optional?
- (question) Should profile data feed personalisation (for example the placement default level) or only owner insights?
- (decision) Non-goals: no paywall, no social features or public profiles, no leaderboards, no passwords, no ads, no selling or sharing of data, no mandatory login, no marketing mail without a separate opt-in.

- (direction) 2026-10-11 owner left the open questions unanswered and asked to proceed; each is resolved below as an ASSUMPTION (A1 to A7), chosen as the safest and simplest default, and the owner can overturn any one with a single later entry naming its id.
- (assumption) A1 Login providers: email magic link plus Google plus GitHub, no passwords stored. Reason: covers most readers and developers with no password surface. Changing it affects: Supabase Auth provider config, OAuth redirect list, the sign-in screen, the privacy page subprocessor list. Resolves the providers question.
- (assumption) A2 Login is never mandatory: reading, playground, chapters, exercises, checks, placement, mock and progress stay fully usable signed out and local-first; an account only adds cross-device progress sync, feedback with identity, and roadmap voting. Reason: keeps the free, no-sign-up promise. Changing it affects: the Guest-first constraint, the non-goal on mandatory login, CAP-2 success, the guest e2e test. Resolves the mandatory-login question.
- (assumption) A3 Email is optional for feedback: anonymous feedback is allowed, rate limited and spam guarded; an email is asked only when the visitor ticks that they want a reply. Reason: lowest friction and least personal data held. Changing it affects: CAP-1 form, feedback.email and feedback.reply_requested, the abuse limits, the consent text. Resolves the required-email question.
- (assumption) A4 Data region: the Supabase project lives in Mumbai (ap-south-1) or the nearest available region, and the feedback and owner routes run in the region closest to it; the privacy page names the region and the owner accepts the standard data processing terms of Supabase and Vercel before launch. Reason: closest to the owner and most readers, and the hosts offer those terms ready-made. Changing it affects: project creation, route region config, the privacy page region and subprocessor lines. Supersedes the earlier Indian or Singapore region assumption and resolves the region and processing-agreement question.
- (assumption) A5 Visibility and voting: feedback is private (owner only) by default; a comment is shown publicly only if its author ticked that it may be shown and the owner approved it, never with name or email; roadmap voting is public and requires sign-in, one vote per account per item, vote counts public, voter identity never public. Reason: privacy by default while still allowing a visible roadmap. Changing it affects: CAP-8, feedback.public_ok and approved_at, roadmap tables and views, RLS policies, the privacy consent text. Resolves the who-reads-feedback and public-board question.
- (assumption) A6 Abuse handling beyond rate limits: per-IP and per-browser limits, honeypot, length cap, daily cap, markup stripping and a hide-in-one-action moderation status; no captcha at launch, a lightweight challenge is added only if a flood happens; signed-in voting limits roadmap abuse. Reason: protects readers from friction until abuse is real. Changing it affects: the feedback route, the form, the privacy page subprocessor list if a challenge vendor is added. Resolves the spam question.
- (assumption) A7 Profile data feeds only owner insights; it does not personalise the site (for example the placement default level). Reason: personalisation would make signed-in and signed-out readers see different sites and widen what is processed. Changing it affects: CAP-3 success, the consent wording, the profile-to-UI wiring. Resolves the personalisation question.
- (decision) CAP-8 Public roadmap and voting (new, next unused id; CAP-1 to CAP-7 unchanged): the owner publishes roadmap items and approves which opted-in feedback comments show publicly; a signed-in reader votes once per item and can withdraw the vote; counts are public and voter identity is not. Ships as phase 4, after sign-in and the owner view. Readers do not create items; feature requests go through CAP-1 and the owner may promote one. Follows from A5.
- (decision) Anonymous feedback privacy: the form carries an unticked box that allows public display (no name or email) after owner approval; the confirmation shows a reference id; deletion on request is by writing to the privacy-page contact address with that id or the email, done within 30 days; the IP address is used only for rate limiting as a salted hash discarded within 24 hours and is never stored on the feedback row. Follows from A3 and A5.
- (decision) Account deletion removes the account, profile, synced records, votes (public counts drop accordingly) and linked feedback within 30 days; feedback not linked to an account is anonymised after 24 months unless deleted sooner on request.
- (question) Which contact address does the privacy page publish for deletion and reply requests? Needed before phase 0 launches.
